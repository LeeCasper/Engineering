### 61. 两套自增 id 撞号是常态，不是巧合

C 端 `user.id` 与后台 `admin_user.id` 是**两套独立的自增空间**，`admin#5` 与 `user#5`
是两个毫不相干的人。`operation_log` 只存 `operator_type + operator_id`，
因此凡是按操作人过滤的地方，**`operator_id = ?` 必须与 `operator_type = 'admin'` 成对出现**：

```sql
(ol.operator_type = 'admin' AND ol.operator_id = ?) OR ol.project_id IN (...)
```

少了类型条件，项目管理员就会看到另一个人的操作记录。这类错误的特征是
**「多看到几条」**——不报错、界面正常，只是审计结论错了。
与第 54 条（`notification` / `admin_notification` 混用）是同一类错误的两个面。

同一道理也适用于 JOIN：`LEFT JOIN admin_user au ON au.id = ol.operator_id AND ol.operator_type = 'admin'`——
类型条件必须在 `ON` 上；挪进 `WHERE` 会让 LEFT JOIN 退化成 INNER JOIN，
把整张表里 `operator_type='user'` 的记录静默丢掉。

### 62. 配置项「改完不生效」必须如实标注

§5.5 的配置表里有几项对应的功能还没做（`sign_in_distance_threshold`、
`route_max_points` 属于 V1.2 的签到与路线，`operation_log_retention` 的清理任务还没写）。
这些值改完**不会立即生效**。

若接口一律返回「保存成功」，管理员会以为自己调好了阈值而实际什么都没发生 ——
那种「配置项存在但没人读」的界面比没有这个界面更糟。因此 `SCHEMA` 里用
`effective: false` + `note` 显式标注，由接口透出给前端如实说明。

另外三条相关的自洽性由 `tests/unit/configLimits.test.js` 锁着：
DEFAULTS 的取值必须在 SCHEMA 的合法区间内（否则系统一出厂就带着一个**改不回去**的坏值——
想恢复默认都会被校验拒绝）；可配置的附件上限之和不得超过传输层 `MAX_FILES`；
订阅消息模板 ID 的键名必须与 `notification.service` 的枚举一致。

### 63. 循环 require 会让方法在运行时变成 undefined

给 `sysConfig.service` 加配置注册表时，曾写成「从 `notification.service.FILTERABLE_TYPES`
推导订阅模板 ID 的键名」—— 而 `notification.service` 恰恰要读配置（`resolveTemplateId`
走 `getRaw` 以复用缓存与默认值回落）。这就形成了循环。

Node 对循环 require 的处理是**返回一个还没填好的 `module.exports`**：
先加载的那个模块拿到的是空对象，且如果是 `module.exports = {...}` 重新赋值，
对方持有的引用永远停在那个空对象上。表现是某个方法在运行时突然是 `undefined`，
**且只在特定加载顺序下复现** —— 典型的「本地好好的、线上偶发」。

解法是**拆掉循环**，不是靠 `require` 的位置绕过去：订阅模板的键名在配置注册表里
显式列出，两边是否漂移交给测试核对（`configLimits.test.js` 拿真实枚举逐个比）。
测试期引用不会形成加载期依赖。

### 64. 注销账号**不能**用 `deleted_at`

直觉上「注销 = 软删除」，但本项目大量查询带 `AND u.deleted_at IS NULL`：
成员列表、提醒收件人、验收单提交人、汇报的 JOIN……

软删一个用户之后，他**历史汇报与验收上的署名会一起消失**（JOIN 直接把他过滤掉），
看起来像「这些活从来没人干过」—— 而 AC-U19 明确要求「历史汇报、验收与账目记录**保留**」。

因此注销用 `anonymized_at` + `status='deleted'` 表达：**行留着**，历史还在，
只是这个人不再是「某个人」。登录态失效由 `requireMini` 检查这两个字段完成。

`openid` 与 `phone` 要**置 NULL 而不是保留**：两列上都有唯一索引，
保留会让手机号无法重新注册（直接违反 AC-U20），也会让同一个微信号再次登录
被匹配到这个已注销的行 —— 「重新注册」会变成「原地复活一个匿名账号」。

**注销还要做三件附带的事**（少一件就留下说不清的中间态）：
解除成员关系（否则项目挂着一个永远不会回应的工长，而 AC-AD58 还把他算作
「人员配齐」）、清掉主工长标记**并给管理员发消息**、删除订阅授权记录。

其中第二件值得单独说：Q11 规定「不能直接移除主工长」，但注销是**用户的法定权利**，
系统无权以「你得先交接」为由拒绝 —— 那是把公司的管理责任转嫁给个人。
折中办法是照做但**不静默**：管理员会收到「请重新指定主工长」的消息。

<a id="c65"></a>

### 65. AC-U15 的完整手机号不违反 AC-U02 的脱敏

两条讲的是不同的事：AC-U02 约束**用户自己**的资料页不完整回显手机号；
AC-U15 的功能是**拨号**，脱敏后的号码拨不出去。

边界靠**可见范围**守，不靠打码：只有业主能调、只返回本项目的工长与监理
（不返回其他业主 —— 多业主之间彼此可见住址与手机号是明显的隐私问题）。

也因此**不做读取留痕**（与门锁密码不同）：门锁密码是物理安全凭证，
泄露的后果是有人能进门；手机号是项目内部的正常协作信息，为它每次点按写审计
只会把 `operation_log` 冲成噪音，让真正的变更记录淹没在里面。
判定「要不要留痕」的标准是**泄露后果**，不是「是不是个人信息」。

### 66. 「我的统计」里混了「我的」与「项目的」，这是刻意的

AC-U14 要求工长端展示「本月汇报数、待整改数、待验收数」。三项里只有第一项
真的是「我的」：后两项统计的是**本项目**处于待整改 / 流转中的验收单数。

理由：多工长场景下只有**主工长**能发起验收（Q11）。若后两项也按提交人过滤，
普通工长看到的永远是 0 —— 对一个「待办」性质的数字来说，恒为 0 比不展示更糟：
他会以为自己没有待办。**统计口径要先问「这个数字给谁看、他看完要做什么」。**

### 67. 「谁是这个项目的管理员」只在一处实现

`adminNotification.notifyProjectAdmin` 自己查 `project.created_by`，
调用方不必（也不能）先把那一列 SELECT 出来传进去。

早先这个逻辑散在定时任务里，需要调用方自己查——然后就漏了那一列，
`if (!created_by) return` 静默短路，管理员那条提醒一条都没发出去
（第 55 条）。**把查询收进被调用方之后，「忘了查某一列」这个错误类别就不存在了。**
同类重构适用于任何「调用方需要先取某个字段才能正确调用」的接口。

### 68. SQL 注释写在模板字符串里时，不能出现反引号

```js
// ❌ 语法错误：missing ) after argument list
db.query(`SELECT a, b,
  -- 注意 dc.deleted_at IS NULL 这个条件
  c FROM t`)
```

反引号会**提前终止模板字符串**。报错指向的是整个 `db.query(...)` 的起始位置，
而真正的元凶是注释里的一个标点 —— 很容易被误判成 SQL 语法问题而去检查 SQL。

注释里要引用列名时直接写 `dc.deleted_at`，不加反引号。

### 69. 「带去重的批量通知」和「普通的批量通知」是两条通道

| 函数 | 用途 | 需要什么 |
| --- | --- | --- |
| `notifyMany` | **同一事件只提醒一次**（未汇报提醒、验收超时） | `reminderType + refType + refId` 拼去重键 |
| `notifyEach` | **每发生一次都要说一次**（设置了门锁密码、密码失效） | 无 |

拿 `notifyMany` 去发一条不需要去重的通知时，`reminderType` 是 `undefined`，
写进 `reminder_log.type`（NOT NULL 的 ENUM）会失败 —— 而失败被 `notifyOnce`
的 try/catch 吞成 `{sent: false}`。**结果是通知一条都发不出去，而日志里看不出异常**，
界面上一切正常，只是没人收到消息。

判断标准只有一句：**这件事需要「同一件事只提醒一次」吗？**
这个坑在 M12 真实踩到过一次（「业主设置了门锁密码」用 `notifyMany` 发）。

### 70. `code` 进日志脱敏名单的副作用：错误日志的 HTTP 状态码被抹掉

`utils/logger.js` 的脱敏是**按键名子串匹配**的。为了让门锁密码
（代码里会写成 `code` / `doorCode` / `codeCipher`）不进日志，`code` 必须进名单
—— 而 `errorHandler` 里记 HTTP 状态码用的字段名恰好也叫 `code`。

于是日志里出现了 `"code":"[REDACTED]"`，排查问题时一头雾水。

**处理方式是把那个字段改名**（`code` → `status`），而不是把 `code` 移出名单：
门锁密码泄露的后果是有人能进业主家，而日志字段名叫什么只是习惯问题。
同理，**Error 实例的 `code` 不受影响** —— `redact` 对 Error 走单独分支
（手工构造 `{name, message, code, stack}`），因此 SQL 错误码 `ER_DUP_ENTRY`
仍然打得出来，那正是排查数据库问题时要看的第一个东西。

`tests/integration/doorCode.test.js` 锁着这两条（脱敏生效 + Error.code 保留）。
