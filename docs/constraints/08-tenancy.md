### 71. 多租户：三层隔离与「没有任何角色是不受限的」

隔离层次从两层变三层：**平台 → 租户 → 项目**。

| 角色 | `tenant_id` | 能看到什么 |
| --- | --- | --- |
| `platform` | NULL | 默认 `1 = 0`（什么都看不到）。持租户授权时只读该租户 |
| `owner` | 有值 | **本租户**全部项目 + 本租户账号/模板/配置 |
| `admin` | 有值 | 本租户内、且被 `created_by` 或 `project_admin_scope` 授权的项目 |

**`dataScope` 里原来那条 `unrestricted: true` 旁路必须彻底删掉。** 超级管理员靠它
让 `projectAccess.load` 跳过校验；多租户下租户 owner「在租户内不受项目限制」，
若继续用 `unrestricted` 放行，load 会连**租户校验**一起跳过 ——
租户 A 的 owner 就能打开租户 B 的项目。现在所有人走同一条 SQL，差别只在 clause。

**跨租户一律 404，租户内无权才 403。** 项目 id 自增可枚举，403 会告诉租户 A
「租户 B 有这么多项目」。这与 C 端的「不泄露」是同一条原则，只是这里跨的是租户边界。

<a id="c72"></a>

### 72. 多租户下三种「全局唯一」必须改成「租户内唯一」

| 对象 | 原来 | 改成 |
| --- | --- | --- |
| 默认阶段模板 | 全系统至多 1 个 | **每个租户各 1 个**（`default_key` 折叠到 `tenant_id`） |
| 系统配置 | 一套全局 | 每个租户一套 |
| 内容页 | 一份 | 每个租户各自维护 |
| 后台用户名 | 全局唯一 | `(tenant_id, username)`，平台账号用生成列折叠为 0 |
| 订阅授权 | `(user_id, template_id)` | `(user_id, tenant_id, template_id)` |

**`clearDefault` 必须按租户清。** 原来它是 `UPDATE ... SET is_default = 0 WHERE is_default = 1`，
加租户之后不改成 `AND tenant_id = ?` 的话，租户 A 设一次默认会把**全平台所有租户**的
默认模板一起清掉 —— 其他租户下次建档直接报「没有默认模板」，而他们什么都没做。

<a id="c73"></a>

### 73. 两处「跨项目串号」，与租户无关但必须一起修

- **`progress_report` 的幂等键缺 project**：`(user_id, client_request_id)`。
  一个同时负责多个项目的工长（现在还可能跨租户）若复用同一个 `clientRequestId`，
  服务层预检会命中**另一个项目**的汇报并直接返回它 —— 跨项目读到别人的数据，
  自己的提交被静默丢弃。唯一键补 `project_id`。
- **`reminder_log` 的去重键缺 project**：`ref_id` 是「上次汇报的时间戳」，
  两个项目的锚点落在同一秒、业主又是同一个人时，会互相把对方的提醒判为「已发过」。
  唯一键补 `project_id_key`（生成列折叠 NULL）。

这两条都是**租户改造之前就存在**的 bug，只是多租户让它更容易触发。

<a id="c74"></a>

### 74. C 端可跨租户，因此「租户」必须由调用方显式给出

一个微信账号可以同时给两家装修公司干活（`user` 表仍然全局唯一）。
这让所有**没有项目上下文**的 C 端接口失去了天然租户：订阅授权、反馈、内容页、联系方式。

规则：
- **能从项目推出租户的**（通知、门锁、记账…）→ 由 `projectId` 反查，调用方不必传。
- **推不出的** → 显式 `tenantId` 参数；用户只属于一个租户时可省略，
  属于多个时返回 400 让他明确指定。**绝不「猜一个」** ——
  猜错的后果是消息、订阅、反馈落到别的公司名下，而界面看起来完全正常。
- **未登录的内容页**（用户协议/隐私政策）→ 不带 `tenantId` 读平台默认版本，
  进入租户后再读该租户的版本。

<a id="c75"></a>

### 75. 哪些表带 `tenant_id`，哪些靠 project 派生

- **显式带列**（会被跨项目查询）：`project`、`stage_template`、`sys_config`、
  `content_page`、`feedback`、`operation_log`、`admin_notification`、`export_task`、
  `admin_login_log`、`user_subscription`、`notification`、`route_plan`。
- **靠 `project` 派生**：`ledger`、`acceptance`、`progress_*`、`project_member`、
  `payment_node`、`reconciliation`、`project_door_code`、`visit_*`。

派生之所以成立，靠的是一条既有不变量：**子表行只按 id 被读取，读完之后必定经过一次
项目级校验**（`projectAccess.load` 或 `findActiveRole`）。新增任何「按 id 直接返回子表数据」
的接口，都必须先校验项目归属 —— 破了这条，租户隔离就出现缺口。

<a id="c76"></a>

### 76. 可空 `tenant_id` 表达「不属于任何单一租户的事件」

`admin_user`（NULL = 平台账号）、`admin_login_log`（用户名猜错时不知道是哪个租户）、
`operation_log`（跨租户事件，如一个同属两家公司的账号注销）、`feedback`（提给平台的）、
`notification`（与项目无关的系统消息）。

**查询侧必须显式处理 NULL**：`tenant_id = ?` 会把平台级事件永久过滤掉，
而它们恰恰是最需要被看到的（登录爆破、跨租户操作）。消息中心对租户筛选用的是
`(tenant_id = ? OR tenant_id IS NULL)`。

<a id="c77"></a>

### 77. 平台账号在**路由层**被拒绝，不是「查出一片空」

除 `/admin/auth/*` 外，所有 `/admin/*` 业务路由都挂 `requireAdmin, requireTenant`
（见各 `routes/admin/*.routes.js`）。平台账号调用时返回 **403**，提示明确说
「平台账号不能访问租户业务接口」。

**不要把它改成「允许调用、按 `1 = 0` 查空」**，三个具体原因：

1. `stage_template` 一类查询方法在缺 `tenantId` 时**直接抛错** —— 空列表的前提不成立，
   平台调用会变成 500；
2. `WHERE tenant_id = ?` 传 NULL 会静默退化成 `tenant_id = NULL`（永远不成立），
   看起来像「没有数据」，掩盖了「这个角色本来就不该在这里」；
3. `1 = 0` 只挡业务数据，挡不住写接口。平台账号建项目时会在
   `resolveTemplateId` 里找不到模板，最终以 500 或诡异的 400 收场。

平台看租户数据的**唯一合法入口**是 P4 的 `platform_access_grant` 时间窗，
那条路径要配独立的中间件、只读约束与逐次留痕，不与普通业务接口共用开关。

### 78. 跨租户不可见的验证方式：每个入口单独断，不能只测列表

`tests/integration/tenancy.test.js` 是隔离的**唯一回归网**。多租户最典型的失败形态是
「列表过滤了、详情忘了」：页面上看不到，换个自增 id 就能打开别家的项目。
因此矩阵对**每个入口**分别断言：

| 入口 | 断言 |
| --- | --- |
| 项目 | 列表、详情、成员、付款节点、修改、删除、归档、批量归档、阶段写操作、导出 |
| 模板 | 列表、详情、改、删、复制、设默认；默认模板每租户各一个 |
| 配置 / 内容页 / 反馈 / 操作日志 / 管理员消息 / 导出任务 / 后台账号 | 各自的列表 + 按 id 直接访问 |

两条语义必须分开断言，不要为了「统一」合并：

- **跨租户 → 404**（与「不存在」同一句提示，避免用自增 id 数别家的项目）；
- **租户内无权 → 403**（同一家公司的人，要能区分「不存在」与「没权限」）。

改任何 `WHERE tenant_id` 之后，先跑这个文件。它不测业务正确性，只测「看不见」——
而「看不见」这件事没有别的办法验证。

<a id="c79"></a>

### 79. 开通租户必须一次成型；配额检查必须锁租户行

`tenant.service.provision` 在一个事务里建四样东西：**租户行 + owner 账号 +
默认阶段模板 + 内容页骨架**。少任一样，客户登录后都会撞上一个像系统故障的
空状态（没有模板就无法建档、没有 owner 就没人能配置），而平台没有任何接口
能补齐半成品租户 —— 只能手工进库收拾。

**刻意不插入 `sys_config` 行。** 读取侧在缺行时回落到代码里的 `DEFAULTS`，
值完全一样；而插一份与默认值相同的行会让后台显示成「已配置」，
运维就再也分不清「我们调过」与「这是出厂值」。注意 `sys_config.tenant_id`
是 **NOT NULL**（迁移 016），所以也不存在「平台级默认配置行」这一层；
要做平台维护默认值，需要新迁移 + 生成列唯一键，不是加一条 INSERT 的事。

**配额（`max_projects` / `max_admin_users`，0 = 不限）的检查顺序不能改：**

1. 在**创建项目/账号的那个事务里**调用 `assertProjectQuota` / `assertAdminQuota`；
2. 它们先 `SELECT ... FOR UPDATE` 锁住 tenant 行，再 `COUNT`。

先 COUNT 再 INSERT 而不加锁，两个并发请求会双双看到「还剩 1 个名额」，
然后各插一条 —— 配额被静默突破。**项目恢复（restore）也要检查**：
软删除的行不计入计数，不检查的话「删一个、建一个、再恢复」就能绕过上限。

### 80. C 端「租户停用/到期只读」挂在路由层，不要下沉到 service

`middlewares/tenantGuard.js` 只拦 `POST/PUT/PATCH/DELETE`，读取一律放行 ——
一个微信账号可能同时属于多个租户，A 租户停用不该让用户连 B 的项目都看不了，
也不该阻止他登录（登录后才能知道 A 为什么不可用）。

挂法：每个 C 端写入路由组 `router.use('/:id', tenantWriteGuard({ resource }))`。
`resource` 决定怎么拿 `project_id`：项目级路由用 `:id` 本身，资源级路由
（汇报/验收/对账/门锁/邀请）回表取 `project_id`，表名来自固定映射。

**为什么不在 service 层逐个判断**：C 端写接口有二十多个。逐处加判断是
「记得加就安全」的约定，漏一个就是一个「停用租户仍能继续写数据」的缺口，
不报错、不告警，只会安静地写进去。**新增 C 端写接口时，必须挂在已有的
受保护路由组下；若确实要新开顶层路由，自己补 `tenantWriteGuard`。**

<a id="c81"></a>

### 81. 平台级事件写 `tenant_id = NULL`，且「已退租」是终态

`tenant.create` / `tenant.update` / `tenant.status` 三条审计日志的
`tenant_id` 一律为 NULL，`target_type='tenant'`。它们不属于被操作租户的
审计流：租户 owner 的日志过滤是 `ol.tenant_id = ?`，看不到平台内部
「为什么停用我」的 reason。平台自己的日志读取界面随 P4 一起做。

状态机只有三条边：`active ↔ suspended`，两者都可 → `archived`。
**`archived` 没有出边**：退租意味着合同结束、数据进入留存期，
恢复一个已退租的租户会让「退租时承诺了什么」无法回答。要重新合作就新开租户。

到期（`expires_at`）不改变 `status`。登录与写操作各自判一次，
这样运营延长到期时间后无需再把状态改回来；列表上的 `expired` 字段
供运营一眼看出「已过期但还没停用」的租户。

### 82. 平台访问租户数据：显式上下文头 + 统一只读 + 逐次留痕

平台默认看不到任何租户数据。排障时由**租户 owner** 授一个窗口
（`POST /admin/platform-grants`，最长 7 天，同一平台账号对同一租户只允许一个
有效窗口），平台随后在业务接口上带 `X-Tenant-Id: <租户 id>` 访问。

**用请求头而不是 `?tenantId=`**：消息、内容页、订阅等接口自己就用
`?tenantId=` 做筛选，同名会互相干扰；查询串也更容易被日志与分享链接带出去。

**授权校验与只读拦截都在 `requireTenant` 这一个入口里完成**：

1. 无请求头 → 403；有请求头但无有效授权 → 403；
2. 租户停用/到期 → 403（即使窗口还有效）；
3. **先写访问日志，再判断是否为写操作** —— 顺序反过来的话，
   「平台持授权尝试修改客户数据」不会留下任何记录，而那正是最该审计的动作；
4. 写方法一律 403，并在日志里留下 `method=POST/PUT/DELETE`。

**授权解析成功后必须把目标租户写进 `req.auth.tenantId`。**
下游的模板、系统配置、内容页、后台账号列表都直接读 `operator.tenantId`；
不写这一行，它们会拿 `null` 去查询：模板直接抛错变 500，配置与内容页会读到
平台默认版本。因此有一条容易踩的规则：

> **不要用 `tenantId != null` 判断「不是平台账号」。** 平台持授权期间
> 那个字段是有效租户 id；身份判断一律看 `role`。

**审计日志写在目标租户名下**（`platform.access_tenant`，`tenant_id = 目标租户`），
租户 owner 在自己的操作日志里能看到平台来过。只记方法与路径，
**不记查询串**（筛选条件里可能有业主姓名、手机号），更不记响应体。

**门锁密码对平台永久不可见，靠的是「结构上没有入口」**：
门锁接口只有 C 端（`requireMini`），平台后台 token 在鉴权第一步就被拒；
后台任何接口都不返回门锁密码。因此它不会因为将来某个查询漏加条件而泄漏。
`tests/integration/platformAccess.test.js` 锁着三条：后台详情里没有密码、
平台 token 打 C 端门锁接口是 401、`operation_log` 里没有明文。

### 83. C 端跨租户：订阅、推送与定时任务的三个具体落点

一个人同时在两家公司干活时，下面三处都必须显式带租户 —— 漏掉任何一处都不会报错，
只会「安静地做错」：

**1. 订阅授权与推送判定**
`user_subscription` 的唯一键是 `(user_id, tenant_id, template_id)`，但
**同一个微信模板 ID 会被多个租户使用**（§5.5 的模板由运营配置，两家公司完全
可能填同一个）。因此 `tryPushSubscribeMessage` 查订阅时必须带 `tenant_id`。
只按 `(user_id, template_id)` 查会随机命中另一家公司的记录：在 A 同意、在 B 拒绝过的
用户可能永远收不到 A 的推送，而站内消息一切正常。`notify()` 也必须把
**解析后的 tenantId** 传给推送，否则模板会从平台默认配置里找（查不到）。

**2. 消息的租户归属**
`notification.tenant_id` 优先取调用方显式传入的，否则由 `projectId` 反查，
**两方面都没有时写 NULL（平台级消息），绝不猜**。按租户筛选时
`(tenant_id = ? OR tenant_id IS NULL)`，平台级消息属于用户自己，不能过滤掉。
未读红点仍是全局口径（第 59 条），与筛选无关。

**3. 定时任务按项目所属租户取配置**
`staleReportReminder` 与 `acceptanceTimeout` 都按每个项目自带的 `tenant_id`
读取各自的阈值（`stale_report_days` / `acceptance_timeout_hours`）。
两条扫描都 `JOIN tenant` 并过滤 `status='active'` 且未到期 ——
停用/到期租户的用户做不了任何处理（C 端只读），继续催办只是噪音。

顺带修掉一处「少 SELECT 一列」的老问题：`listTimeoutCandidates` 漏选了
`project_stage_id`，导致超时提醒永远写成「验收单」而不是阶段名。
这是 CLAUDE.md 第 39、55 条同一类错误的第三次出现 —— **凡是靠某列做展示或拼键，
先确认它在 SELECT 列表里**。

**去重键扩了，释放逻辑必须同步扩。** `reminder_log` 的唯一键在迁移 016 里
加了 `project_key`，但 `releaseReminderClaim` 当时仍只按
`(type, ref_type, ref_id, target_user_id)` 删除 —— 两个项目的锚点落在同一秒、
业主又是同一个人时，释放其中一个会把**另一条已经发出去的**占用一起删掉，
下一轮扫描就会重复推送。**键的每一段都要在 claim 与 release 两处同时出现**，
与 CLAUDE.md 第 49 条（索引与服务层预检必须完全一致）是同一条原则。
